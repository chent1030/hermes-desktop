# Platform Phase 2 Remaining Gaps Review

## 1. 目的

这份文档用于在 `platform-phase2-desktop-closure` 分支上，对第二份计划当前状态做一次最新事实盘点，明确：

- 已经闭环的能力
- 仍然保留的剩余缺口
- 下一阶段建议优先级

## 2. 当前已基本闭环的能力

结合当前代码、测试和最新验证记录，以下能力已经基本成型：

- 租户登录主入口
- 在线初始化主链路
- 平台模型下发与默认模型自动选中
- Skill 只读清单下发
- 本地 Skill 探测与状态回填
- 手动下载 Skill
- 显式 `session-recovery` 状态面
- 聊天审计主链路
- 运行审计已覆盖：
  - `run.model.*`
  - `run.skill.download.*`
  - `run.skill.sync.*`
  - `run.tool.*`
- 初始化进度展示
- 审计总状态 / 本地缓冲状态 / 平台审计服务状态展示
- 管理端最小模型中心、Skill 中心、审计中心、会话中心
- 平台后台本地测试 + 真实 PostgreSQL live tests（认证、桌面执行端接口、审计中心、会话中心、模型配置、Skill 目录）

## 3. 剩余缺口

### Gap 1：审计事件族仍是分层模型，而不是单一大一统命名

当前事件分层大致如下：

- `auth.*`
- `workspace.*`
- `chat.*`
- `run.*`

这符合当前设计边界：

- `auth.*` 负责认证链路
- `workspace.*` 负责初始化 / 生命周期
- `chat.*` 负责会话中心聚合
- `run.*` 负责非聊天运行行为

但如果后续平台希望直接做“统一执行大盘”或“按运行面一键筛选”，可能还需要额外的投影视图或更高层分类字段，而不只是继续扩事件名。

### Gap 2：管理端运维视图功能缺口已基本收口，仅剩更高阶分析演进

当前管理端已经支持：

- 审计中心：
  - `eventType` 精确筛选
  - `eventPrefix` 事件族筛选
  - 账号关键字筛选
  - `payload` 关键字检索
  - `run.*` 事件摘要展示
  - 基于当前结果集的事件族统计与失败摘要图表
- 会话中心：
  - 聊天会话聚合
  - `run.tool.*` 最小执行摘要
- 从会话中心一键打开对应会话的审计视图

因此 Gap 2 对应的“最小运维工作台”能力已经基本闭环，当前若继续演进，重点将不再是基础检索，而更偏向：

- 服务端全量统计
- 趋势图 / 时间序列图
- 更复杂的跨租户运维分析

### Gap 3：Gateway 仍保留进程与 IPC 能力，只是桌面端界面隐藏

这项目前仍符合既定需求，因为已确认要求是“只在桌面端界面隐藏”。

从代码事实上看：

- `src/main/index.ts` 仍注册 `start-gateway` / `stop-gateway` / `gateway-status`
- `src/preload/index.ts` 与 `src/preload/index.d.ts` 仍暴露对应 API

因此当前达成的是：

- UI 不展示 Gateway
- 进程能力与 IPC 能力仍然保留

如果后续产品口径升级为“第一阶段彻底不可触达 Gateway”，则需要单独切片处理。

## 4. 建议优先级

如果继续按“平台稳定优先”推进，建议顺序如下：

1. **优先评估 Gap 1**：确认平台侧是否需要统一执行大盘，再决定是补投影视图还是继续扩事件模型
2. **Gap 3 暂不处理**：除非产品口径从“界面隐藏”升级为“能力禁用”
3. **高阶运维分析后置**：仅当平台侧出现更强的监控 / 报表诉求，再引入服务端聚合与趋势图

## 5. 本轮结论

当前分支已经完成第二份计划的大部分主闭环，剩余问题不再是“缺主功能”，而主要是：

- 审计分层模型是否需要进一步抽象
- Gateway 能力边界是否要从“隐藏”升级为“禁用”
- 是否要继续建设更高阶的统计 / 趋势分析能力

后续仍建议保持“小切片 + 文档 + 测试 + 推送”的节奏推进。
