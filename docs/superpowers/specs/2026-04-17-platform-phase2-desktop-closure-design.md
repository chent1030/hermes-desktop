# Hermes Desktop 平台化改造第二份设计文档

## 1. 背景

第一份计划已经完成平台底座建设，重点解决了以下问题：

- 独立管理端技术栈落定为 `React + Rust + PostgreSQL`
- 平台认证、基础 RBAC、生产部署骨架已经建立
- 管理端可以作为后续桌面端接入的统一控制面

第二份计划不再讨论“要不要平台化”，而是把现有桌面端真正接入平台主链路，形成“登录、初始化、工作区、运行审计”的完整闭环。

这一阶段的核心目标，不是做零散接口对接，而是把桌面端从当前本地单机主流程切换为：

- 以租户登录为唯一主入口
- 以在线初始化为唯一配置入口
- 以平台授权模型为唯一模型来源
- 以平台 Skill 清单 + 本地探测状态为 Skill 视图来源
- 以统一审计总线承接聊天与运行事件

## 2. 本期范围与边界

### 2.1 本期必须交付

第二份计划纳入范围的能力如下：

1. 桌面端租户登录
2. 在线初始化
3. 模型配置下发与默认模型自动选中
4. Skill 只读清单下发
5. Skill 本地探测与状态回填
6. 本机受控重装配
7. 刷新令牌自动续期
8. 聊天与运行审计完整接入
9. 审计中断告警与恢复补传
10. 主工作区大闭环接入

### 2.2 本期明确不做

以下内容不纳入第二份计划：

- Skill 上传 / 发布管理
- Skill 自动安装 / 自动卸载
- 模型配置本地持久化
- 离线模式
- 跨重启免登录
- SSO
- Windows 全量兼容收口

## 3. 用户决策与方案结论

本次设计阶段已经确认以下关键产品决策：

- 平台形态采用单套平台、多租户共用
- 桌面端必须联网
- 不兼容旧数据
- 应用重启后必须重新登录、重新在线初始化
- 模型只显示平台授权模型，且必须存在默认模型自动选中
- Skill 展示全局 Skill 与租户 Skill 两类清单
- Skill 第一阶段只展示与手动下载，不自动执行安装
- 配置和令牌只保存在内存
- 审计中断时允许聊天继续，但必须持续告警，并在恢复后补传
- 第二份计划采用“大闭环”接入，不只改聊天页

在三种候选路径中，最终采用：

### 3.1 方案 A：初始化闭环优先

- 先把租户登录、初始化、工作区上下文、模型来源、Skill 只读清单、审计总线统一起来
- 再把主工作区现有页面逐步接到新壳层

选择该方案的原因：

- 最能降低“旧本地流程”和“新租户流程”长期并存的风险
- 能保证后续实现阶段围绕一个稳定状态机推进
- 有利于把模型、Skill、审计统一收口到平台边界

## 4. 总体架构与主数据流

第二份计划的逻辑分层如下：

1. **认证与会话层**
   - 负责租户登录、访问令牌、刷新令牌、运行期续期
   - 约束是“进程内续期、跨重启失效”
2. **初始化编排层**
   - 负责登录后在线拉取 bootstrap、模型配置、Skill 清单
   - 负责关键阶段失败阻断与重试
3. **本机受控装配层**
   - 负责把平台配置装配到桌面端运行时
   - 仅保存在内存，不写本地持久化配置
4. **主工作区壳层**
   - 负责向所有页面分发统一租户上下文、模型状态、Skill 视图和审计状态
5. **审计总线**
   - 负责聊天、运行、Skill 状态变化、登录登出和初始化事件的统一采集、上报与补传

整体主数据流如下：

1. 应用启动
2. 进入租户登录页
3. 登录成功后进入初始化状态机
4. 拉取平台基础上下文
5. 拉取授权模型并自动选中默认模型
6. 拉取 Skill 只读清单
7. 执行本地 Skill 探测并回填状态
8. 完成本机受控重装配
9. 进入主工作区
10. 运行期持续处理刷新令牌、审计上报和失败补传

## 5. 桌面端启动链路设计

### 5.1 新的主状态机

桌面端主入口改为以下状态机：

1. `Login`
2. `Initializing`
3. `Workspace`
4. `SessionRecoveryOrLogout`

关键原则如下：

- 旧 `Welcome / Install / Setup` 流程退出主路径
- 登录成功不等于初始化完成
- 初始化未完成不得进入主工作区
- 刷新令牌彻底失败后必须清空内存态并回到登录页

### 5.2 与当前代码结构的关系

当前 `App.tsx` 仍以本地安装检查驱动页面切换，第二份计划需要改为：

- `App.tsx` 只负责新状态机切换
- 新增统一工作区壳层承接已初始化的运行上下文
- `Layout.tsx` 从“直接持有全局主状态”调整为“消费统一上下文的工作区布局”

## 6. 配置中心接口与初始化数据流

### 6.1 平台接口分层

建议桌面端使用以下平台接口分层：

1. **认证接口**
   - `/api/auth/login`
   - `/api/auth/refresh`
2. **初始化上下文接口**
   - `/api/desktop/bootstrap`
3. **模型配置接口**
   - `/api/desktop/model-profiles`
4. **Skill 清单接口**
   - `/api/desktop/skills/catalog`
5. **审计接口**
   - `/api/audit/events:batch`
   - `/api/audit/health`

接口边界约束如下：

- 桌面端拿到的是“面向执行端的收敛视图”，不是管理端完整配置实体
- 模型接口只返回当前用户可见模型、默认模型、必要运行字段
- Skill 接口只返回展示与下载所需信息，不负责自动安装

### 6.2 混合拉取顺序

登录成功后，初始化编排层按以下顺序工作：

1. 拉取 `bootstrap`
2. 拉取授权模型
3. 校验默认模型存在并自动选中
4. 拉取 Skill 只读清单
5. 执行本地 Skill 探测
6. 将模型、默认值、功能开关、审计策略装配进内存态
7. 放行进入主工作区

### 6.3 初始化失败规则

以下情况属于初始化阻断错误：

- `bootstrap` 拉取失败
- 授权模型为空
- 默认模型缺失
- Skill 清单关键字段缺失到无法构建展示视图

阻断处理规则：

- 停留在初始化页
- 展示明确阶段和错误原因
- 提供重试按钮
- 保留当前进程内认证态以便直接重试

## 7. 模型配置设计

### 7.1 模型来源规则

模型来源只允许来自平台授权配置：

- 用户不能看到未授权模型
- 默认模型必须在初始化阶段自动选中
- 不允许出现“进入工作区后无当前模型”的空态

### 7.2 本地保存规则

本期不做本地持久化：

- 访问令牌只在内存保存
- 刷新令牌只在内存保存
- 当前模型选择只在当前进程内有效
- 应用退出后必须重新登录并重新初始化

## 8. Skill 清单与本地探测设计

这是本次设计中需要特别强调的边界。

### 8.1 Skill 主数据分为两层

#### 平台清单层

平台清单决定：

- 用户有权看到哪些全局 Skill
- 用户有权看到哪些租户 Skill
- 对应版本、下载地址、说明、展示元数据

#### 本地探测层

本地探测只负责识别：

- 本机已安装哪些 Skill
- 当前版本是否匹配平台清单
- 当前 Skill 是否可用
- 路径或运行时是否异常

### 8.2 统一展示模型

Skill 页展示结果来自“平台清单 + 本地探测状态”的合并视图。

推荐的用户可见状态包括：

- 未下载
- 已下载未装配
- 已安装可用
- 版本落后
- 本地异常

### 8.3 边界约束

- 本地探测必须保留
- 本地探测只能做状态识别与可用性判断
- 本地探测不能反向决定平台授权范围
- 第一阶段只支持手动下载，不支持自动安装和自动移除

## 9. 主工作区大闭环接入

### 9.1 工作区壳层

建议新增以下工作区结构：

1. `WorkspaceShell`
   - 挂载租户会话、bootstrap 上下文、模型状态、Skill 视图、审计状态
2. `WorkspaceGuard`
   - 拦截令牌失效、初始化失效、关键配置缺失
3. `WorkspaceLayout`
   - 负责侧栏与内容区布局，并根据平台功能开关裁剪导航

### 9.2 现有页面接入原则

#### Chat / Sessions

- 接入统一租户上下文
- 接入统一模型状态
- 接入审计总线

#### Models

- 改为平台授权模型展示与切换页
- 只显示可见模型与默认模型状态

#### Skills

- 展示全局 Skill 与租户 Skill 两类只读清单
- 同时显示本地探测状态

#### Settings

- 以账户、语言、初始化状态、审计状态、退出登录为主
- 弱化旧本地安装配置内容

#### Gateway

- 第二份计划只在桌面端导航中隐藏入口
- 底层代码可暂留，不作为本轮主清理目标

### 9.3 导航与全局状态规则

- 导航由平台功能开关和产品阶段统一裁剪
- 工作区应持续展示当前租户、当前账号、当前模型、审计状态
- 退出登录必须清空所有内存态并返回登录页

## 10. 审计缓冲、告警与补传

### 10.1 审计总线分层

审计总线分为四层：

1. **事件采集层**
   - 采集登录、登出、初始化、聊天、模型切换、Skill 探测、Skill 手动下载触达、工具运行等事件
2. **本地缓冲层**
   - 在内存中维护待发送队列、重试队列和告警状态
3. **上报传输层**
   - 批量上报平台审计接口，支持退避与恢复补传
4. **告警展示层**
   - 将审计状态显示给工作区和关键页面

### 10.2 受控降级原则

用户已明确选择：

- 审计异常时允许聊天继续
- 但必须持续告警
- 审计恢复后需要优先补传

因此本期的处理规则是：

- 平台审计接口短暂失败时，聊天和本机运行可以继续
- 审计失败不能静默
- 界面要显示“审计异常 / 补传中”等状态
- 恢复后先补传旧事件，再恢复实时上报

### 10.3 明确不是离线模式

以下边界必须写死：

- 不把积压事件写入本地磁盘
- 不把审计中断包装成正式离线能力
- 应用退出时，未补传事件会随进程结束而丢失
- 必须通过平台告警与可观测性暴露这一风险

### 10.4 队列与异常策略

- 队列必须有容量上限
- 上限逼近时提升告警等级
- 发生 `401 / 403` 时，应视为认证链路失效并转交刷新令牌流程
- 刷新失败后，回到登录页并放弃当前内存态

## 11. 错误处理策略

### 11.1 P0 阻断错误

以下错误必须阻断进入主工作区：

- 登录失败
- `bootstrap` 失败
- 授权模型为空
- 默认模型缺失
- 刷新令牌彻底失效

### 11.2 P1 受控降级错误

以下错误允许业务继续，但必须告警并提供重试：

- 审计接口异常
- Skill 本地探测异常
- Skill 下载链接临时不可用

### 11.3 P2 局部错误

以下错误只影响局部模块：

- 懒加载页面失败
- 非关键统计接口失败
- 局部展示字段缺失

## 12. 测试与验收边界

### 12.1 测试分层

第二份计划至少要覆盖以下测试层级：

1. 平台 API 契约测试
2. 桌面端状态机测试
3. 页面接入测试
4. 联调冒烟测试

### 12.2 必须验收通过的结果

验收通过标准如下：

1. 应用启动默认进入新租户登录主路径
2. 登录后必须完成在线初始化才可进入主工作区
3. 平台默认模型自动选中
4. Skill 页展示平台授权清单与本地探测状态
5. Skill 仅支持手动下载，不自动安装
6. 聊天与运行产生审计事件，并支持中断后补传
7. 应用重启后必须重新登录并重新初始化
8. Gateway 在桌面端导航中隐藏

### 12.3 本期不作为验收项

- Skill 上传 / 发布
- 离线模式
- SSO
- Windows 全量支持

## 13. 生产可用补充要求

虽然第二份计划聚焦桌面端闭环，但仍需满足生产可用要求：

- 平台端需要有初始化失败、审计积压、补传恢复、Skill 下载失败等可观测指标
- 桌面端需要支持版本回滚，但不能回退到旧单机模式作为正式主路径
- 建议先在内部测试租户完成全链路灰度验证，再逐步放量

## 14. 最终结论

第二份计划的本质，是把 `hermes-desktop` 从“本地安装驱动的单机桌面应用”改造成“平台控制下的联网执行端”。

本期最重要的不是某一个页面，而是以下五条边界同时成立：

1. 新租户登录主路径成立
2. 在线初始化状态机成立
3. 平台模型来源成立
4. Skill 平台清单 + 本地探测双层视图成立
5. 审计可告警、可补传、但不演变为离线模式

只要这五条边界稳定，后续再扩展 Skill 发布、SSO、Windows 和更复杂的平台能力，成本才可控。
