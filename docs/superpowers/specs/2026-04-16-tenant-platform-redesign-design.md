# Hermes Desktop 租户平台化改造设计文档

## 1. 背景与目标

当前仓库 `hermes-desktop` 的产品形态，本质上是一个面向单机用户的本地桌面客户端：

- Electron 桌面端同时承担安装、配置、运行与管理职责
- 主流程默认围绕本地 `~/.hermes` 目录组织
- 安装器和运行路径明显偏向 Unix/macOS 假设
- i18n 框架已经存在，但当前仅提供英文资源
- `Gateway` 仍然作为正式桌面端模块暴露
- 尚未具备租户、统一认证、后台管理、配置下发、中心化 Skill 管理与平台级审计能力

本次改造的目标，不是做一次局部功能增强，而是把现有“本地单机版 Hermes Desktop”升级为“桌面执行端 + 独立管理平台”的平台化体系。

### 1.1 目标

本次设计确认的总体目标如下：

1. 新建独立管理平台，采用 `React + Rust + PostgreSQL` 技术栈，并以 `Docker` 方式交付生产可用部署
2. 管理平台采用单套部署、多租户共用模式
3. 桌面端只保留租户登录模式，取消当前本地单机模式
4. Agent 继续在用户本机运行，但运行配置由管理平台统一下发
5. 管理平台提供租户、用户、角色、权限、模型配置、Skill Hub、审计与会话中心能力
6. Skill Hub 采用仓库型设计，并接入京东云对象存储保存 Skill 包与资源
7. 桌面端支持中英双语，同时在第一阶段隐藏 `Gateway` 界面入口
8. 第一阶段以“平台稳定优先”为交付导向，Windows 支持采用后续阶段推进

### 1.2 非目标

以下内容明确不纳入第一阶段交付：

- 不兼容旧本地数据迁移
- 不保留离线模式
- 不在第一阶段交付 SSO
- 不开放桌面端 `Gateway` 产品入口
- 不在第一阶段完成 Windows 全量支持
- 不引入复杂审批流、Skill 市场化共享、重型不可篡改账本等高复杂度平台能力

## 2. 为什么要分阶段，以及为什么优先做平台

用户提出的需求包含六个方向：Windows 支持、租户登录模式、管理端、Skill Hub、模型配置下发、中文界面、隐藏 Gateway。经分析，这些内容并不是一个同层级的单一需求，而是横跨多个系统边界：

- 桌面端产品流与 UI
- 平台认证与多租户权限
- 平台配置中心
- Skill 仓库与分发
- 审计与会话中心
- 跨平台兼容与安装运行时

如果把这些能力一次性并行改造，风险会集中出现在以下几个方面：

- 桌面端和管理端接口会高频变化，导致返工
- 平台边界不清，会把“本地单机遗留逻辑”继续带入新架构
- Windows 支持会放大运行时、路径、安装器与本地执行问题，拖慢平台底座建设
- Skill 管理、模型下发和审计回传如果没有稳定平台承载，桌面端无法形成受控闭环

因此，本次设计选择以下顺序：

1. **先建设平台底座**
   - 先把租户、用户、角色、权限、认证、数据库、部署骨架建立起来
   - 目的是先形成稳定的管理中台和 API 边界
2. **再做配置下发与桌面端登录改造**
   - 让桌面端从本地配置中心转为受控执行端
3. **再接入 Skill Hub**
   - 在清晰的租户与权限体系下管理全局 Skill 和租户 Skill
4. **再补平台级审计与会话中心**
   - 保证平台不仅能“管配置”，还能“管运行结果”
5. **最后做桌面端产品收口与 Windows 后续推进**
   - 中英双语、隐藏 Gateway、清理旧流程先完成
   - Windows 作为后续阶段独立推进，避免阻塞平台首发

这个顺序与“平台稳定优先”的目标一致，也能最小化首期的系统性返工风险。

## 3. 方案选型与结论

设计阶段讨论过三种推进方案：

### 3.1 方案 A：平台先行，桌面端受控化改造（最终选定）

- 先建设独立管理平台
- 桌面端第一期聚焦登录、配置拉取、本机运行、审计回传
- Skill、模型、权限与会话都由平台统一承载

**优点**

- 最符合“平台稳定优先”的目标
- 系统边界清晰，便于后续扩展 Windows、SSO 与更复杂能力
- 能快速形成租户化、受控化、可审计的完整产品闭环

**缺点**

- 桌面端会发生较明显的产品形态变化
- 首期管理平台的建设压力较大

### 3.2 方案 B：平台与桌面端并行重构

- 平台和桌面端同时大幅改造

**不选原因**

- 接口和流程会频繁变化
- 联调和返工风险高
- 不利于先把平台打稳

### 3.3 方案 C：先去本地化桌面端，再补平台

- 先把当前桌面端本地模式拆掉，再慢慢补平台

**不选原因**

- 会形成一个“既不完整平台化，也不完整本地化”的过渡状态
- 用户价值和架构价值都不稳定

## 4. 总体架构

### 4.1 逻辑分层

整个系统在第一阶段拆成三层：

1. **管理平台**
   - 采用 `React + Rust + PostgreSQL`
   - 负责认证、租户、用户、角色、权限、模型配置、Skill Hub、会话与审计
2. **桌面端**
   - 基于现有 `Electron + React` 项目改造
   - 从本地单机控制台改造成在线认证后的受控执行端
3. **本机运行时**
   - Hermes Agent 仍在用户机器执行
   - 但运行配置来源改为平台统一下发

### 4.2 关键职责边界

#### 管理平台负责

- 租户与用户管理
- 账号密码登录与后续 SSO 扩展预留
- 角色与权限控制
- 模型配置与密钥管理
- Skill 仓库、版本、发布与分发范围
- 会话数据中心
- 合规审计中心
- 生产部署与运维能力

#### 桌面端负责

- 租户登录
- 拉取平台授权配置
- 组装本机运行环境
- 在授权范围内供用户选择模型
- 同步平台允许的 Skill 清单
- 运行本地 Agent 并回传会话与审计数据

#### 本机运行时负责

- 按平台下发配置执行模型调用
- 执行 Skill / Tool
- 产生会话、工具调用和关键日志

## 5. 管理平台技术架构

### 5.1 技术栈

- 前端：`React`
- 后端：`Rust`
- 数据库：`PostgreSQL`
- 文件对象存储：京东云对象存储
- 交付形态：`Docker`

### 5.2 部署形态

平台采用**单套平台、多租户共用**模式：

- 一个后台系统服务多个租户
- 通过租户维度进行数据与权限隔离
- 不为每个租户独立部署一套系统

### 5.3 生产可用部署要求

第一阶段不是开发演示版，而是生产可用交付，因此至少需要：

- Docker 化部署方案
- 反向代理 / TLS / 域名入口
- PostgreSQL 持久化
- 平台关键配置持久化
- 备份与恢复机制
- 结构化日志
- 健康检查
- 基础监控与告警

## 6. 领域模型设计

第一阶段推荐的核心领域对象如下：

### 6.1 Tenant

租户是一级隔离边界，用于承载：

- 用户
- 角色绑定
- 模型配置
- 租户 Skill
- 会话
- 审计数据

### 6.2 User

用户属于某个租户，可通过管理端或桌面端登录平台，并被授予一个或多个角色。

### 6.3 Role / Permission

第一阶段采用 `RBAC` 作为权限模型：

- 便于快速落地
- 对租户后台和平台后台都足够清晰
- 可在后续阶段再演进到更细粒度的策略体系

### 6.4 Model Profile

模型配置对象用于表达：

- 可用模型集合
- 提供商类型
- 默认模型
- 模型凭证
- 租户可见范围
- 客户端可选范围

### 6.5 Skill Registry / Skill Version / Skill Distribution

Skill 相关对象需要拆为三层：

- `Skill Registry`：Skill 基础定义
- `Skill Version`：版本元数据和包引用
- `Skill Distribution`：租户可见范围、是否启用、默认版本与同步策略

### 6.6 Session / AuditEvent

平台统一承载：

- 聊天会话与消息内容
- Tool / Skill 调用记录
- 关键运行日志
- 认证、配置刷新、设备关联等审计事件

## 7. 权限模型设计

### 7.1 角色分层

第一阶段建议至少支持以下角色层级：

#### 超级管理员

负责：

- 管理租户
- 管理平台级参数
- 管理全局 Skill
- 管理全局模型模板
- 查看平台级审计视图

#### 租户管理员

负责：

- 管理本租户用户
- 绑定角色
- 管理租户 Skill
- 管理租户模型配置
- 查看本租户的会话与审计数据

#### 普通用户

负责：

- 登录桌面端
- 在授权范围内使用模型和 Skill
- 查看自己的使用范围与会话

### 7.2 权限边界原则

- 超级管理员可以管理全局 Skill
- 租户管理员可以管理租户 Skill
- 普通用户不直接管理平台资源
- 审计导出权限必须显式受 RBAC 控制
- 所有平台接口都要显式绑定租户上下文和操作者身份

## 8. 认证与登录设计

### 8.1 首期认证方式

第一阶段提供：

- 账号密码登录

架构上预留：

- SSO / OAuth 接入能力

### 8.2 桌面端登录模式

桌面端只保留租户登录模式，不再支持本地单机模式。新主路径为：

1. 用户输入租户标识、账号、密码
2. 桌面端向平台认证服务申请访问令牌
3. 认证成功后，桌面端拉取用户与租户上下文
4. 再拉取模型授权范围、Skill 清单、密钥材料与策略参数
5. 完成本机运行环境装配后进入主工作区

### 8.3 在线约束

桌面端必须联网：

- 登录依赖平台在线
- 配置拉取依赖平台在线
- 运行过程依赖平台在线
- 审计与会话回传依赖平台在线

不设计长期离线能力，也不设计旧本地模式兜底。

## 9. 模型配置与密钥下发设计

### 9.1 设计原则

- 模型配置由平台统一管理
- 平台将模型配置和密钥下发到桌面端
- 桌面端用户可以选模型，但必须限制在平台授权范围内

### 9.2 平台职责

平台需要维护：

- 模型提供商
- 模型列表
- 默认模型
- 模型可见范围
- 模型密钥
- 租户可选策略

### 9.3 桌面端职责

桌面端需要：

- 安全地使用平台下发的密钥与配置
- 尽量减少本地落盘范围
- 仅在授权范围内展示和切换模型
- 在令牌失效或配置失效时进入异常态

### 9.4 安全边界

由于密钥需要下发到桌面端，第一阶段必须接受一个现实：

- **本地绝对安全无法保证**

因此第一阶段的目标是“降低风险”，而不是“消除风险”，重点措施包括：

- 平台端加密存储密钥
- 桌面端最小化本地落盘
- 令牌过期与刷新机制
- 将设备标识纳入审计上下文

## 10. Skill Hub 设计

### 10.1 设计结论

Skill Hub 第一阶段采用**仓库型**设计，而不是简单目录型：

- Skill 在平台上传
- Skill 在平台托管
- Skill 按版本管理
- Skill 按租户分发

### 10.2 技术职责分离

#### PostgreSQL 保存

- Skill 元数据
- Skill 版本关系
- 租户归属
- 发布状态
- 分发规则
- 对象存储引用和哈希

#### 京东云对象存储保存

- Skill 包
- 图标
- 附件
- 其他二进制资源

### 10.3 Skill 分层

#### 全局 Skill

- 由超级管理员创建和发布
- 可分发给多个租户

#### 租户 Skill

- 由租户管理员或超级管理员创建
- 仅在所属租户范围内可见和可用

### 10.4 分发与同步链路

1. 管理端上传 Skill 包
2. 平台写入 Skill 与版本元数据
3. Skill 文件写入京东云对象存储
4. 平台定义可见范围、启用状态与默认版本
5. 桌面端登录后拉取授权 Skill 清单
6. 桌面端按平台规则同步 Skill 到本地运行环境

### 10.5 第一阶段暂缓事项

- 不做复杂审批流
- 不做多阶段灰度发布
- 不做跨租户市场化共享
- 不做复杂依赖自动解析

## 11. 桌面端改造设计

### 11.1 改造方向

现有桌面端需要从“本地单机控制台”转成“在线认证后的受控执行端”。

### 11.2 主流程变化

当前主流程近似为：

- `Splash -> Welcome -> Install -> Setup -> Main`

新主流程应调整为：

- `Splash -> Tenant Login -> Online Initialization -> Main`

### 11.3 核心改造点

1. 删除本地单机产品定位
2. 取消本地单机初始化主路径
3. 新增租户登录入口
4. 新增平台配置容器
5. 新增在线状态校验
6. 新增审计回传链路
7. 在桌面端隐藏 `Gateway`
8. 提供中英双语支持

### 11.4 界面语言策略

第一阶段支持：

- `zh-CN`
- `en`

不是仅切到中文，而是做成完整双语能力。

### 11.5 Gateway 边界

第一阶段仅隐藏桌面端 `Gateway` 界面入口：

- 底层代码暂时保留
- 不作为第一阶段对外功能暴露

### 11.6 Windows 策略

Windows 支持采用后续阶段推进，不作为第一阶段阻塞项。

## 12. 会话同步与合规审计设计

### 12.1 设计目标

第一阶段的审计能力目标是**合规审计**，而不是基础日志查看。

### 12.2 审计范围

平台需要接收并保存以下数据：

- 聊天内容与会话元数据
- Skill 调用记录
- Tool 调用记录
- 成功 / 失败状态
- 耗时
- 关键错误信息
- 登录事件
- 配置刷新事件
- 关键运行日志

### 12.3 审计链路

推荐链路如下：

1. 桌面端在关键节点采集事件
2. 事件进入本地审计缓冲层
3. 附加租户、用户、设备、会话、时间戳、事件类型等上下文
4. 通过审计接口批量或流式写入平台
5. 平台写入会话主表与审计索引

### 12.4 合规能力

第一阶段至少需要：

- 留存策略
- 审计导出
- 责任追踪链路
- 平台端“不可随意业务改写审计主记录”的基础防篡改边界

### 12.5 不采用的高复杂度方案

第一阶段不直接承诺：

- 重型不可篡改账本
- 区块链式审计存证
- 超复杂实时风控编排

### 12.6 风险说明

全量审计会显著增加：

- PostgreSQL 存储压力
- 检索压力
- 导出压力

因此平台设计必须同时考虑：

- 分表 / 索引策略
- 留存策略
- 导出策略
- 高容量日志与会话的查询边界

- 桌面端登录
- 本机运行
- 会话回传
- 审计查询

### 15.4 部署验证

覆盖：

- Docker 部署
- 反向代理
- 健康检查
- 持久化卷
- 备份恢复

## 16. 主要风险

### 16.1 桌面端形态切换风险

现有项目是本地单机产品，本次要切换为在线受控模式，改造幅度较大。

### 16.2 本地密钥风险

模型密钥下发到本机，意味着只能降低风险，无法做到绝对安全。

### 16.3 审计规模风险

全量审计会对数据库容量、索引、查询和导出能力提出较高要求。

### 16.4 Skill 同步一致性风险

平台与桌面端之间的 Skill 版本同步、更新和回滚策略需要设计清楚，否则会出现执行环境不一致。

### 16.5 多租户权限风险

多租户共享平台意味着任意越权都会成为严重问题，因此权限边界、租户上下文和审计追踪必须从第一天就建立。

## 17. 验收标准

第一阶段以“平台稳定优先”为验收导向，最低验收标准应包括：

1. 平台可在生产可用 Docker 环境中部署运行
2. 租户、用户、角色、权限闭环可用
3. 桌面端可以完成租户登录与在线初始化
4. 平台可下发模型配置和授权 Skill 清单
5. 用户可在授权范围内选择模型并在本机运行 Agent
6. 聊天记录、会话与审计事件能够回传平台
7. 平台支持按租户维度查询和导出审计记录
8. 桌面端支持中英双语，且隐藏 Gateway 入口

## 18. 后续阶段展望

以下能力作为后续阶段考虑：

- Windows 支持
- SSO / OAuth
- 更细粒度的策略模型
- Skill 审批流
- Skill 市场化共享
- 更强的审计防篡改方案

## 19. 结论

本次改造的本质，不是简单给桌面端增加几个配置项，而是将 `hermes-desktop` 从本地单机工具升级为企业可管控、可审计、可租户化运营的平台产品。

最终设计结论如下：

- 第一阶段采用“平台先行，桌面端受控化改造”的路线
- 平台使用 `React + Rust + PostgreSQL + Docker`
- 平台采用单套多租户模式
- 桌面端只保留租户登录模式
- Agent 仍在本机运行，但运行配置由平台统一下发
- Skill Hub 采用仓库型设计，并接入京东云对象存储
- 模型配置和密钥由平台管理并下发到桌面端
- 会话与审计统一回传平台，并按合规审计能力设计
- 第一阶段聚焦平台稳定与闭环打通，Windows 与 SSO 放到后续阶段

这份设计文档可直接作为下一步实施计划拆解的依据。
