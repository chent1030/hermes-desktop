# Platform Session Audit Linkage Design

## 1. 背景

当前平台管理端已经具备：

- 审计中心：支持 `eventType`、`eventPrefix`、账号、`payload` 关键字筛选
- 会话中心：支持聊天会话聚合、失败筛选、时间范围筛选，以及 `run.tool.*` 最小摘要

但排障仍存在一个断点：

- 运维先在会话中心看到异常会话
- 然后还要手动切到审计中心，自己输入 `sessionId` 做检索

这会增加排障步骤，也无法形成真正的“会话 -> 审计”闭环。

## 2. 目标

本次只补一个最小联动动作：

- 在会话中心每条会话摘要上增加“打开审计”动作
- 点击后自动把该 `sessionId` 带入审计中心检索，并立即刷新审计列表

目标是减少人工复制查询条件的动作，不额外引入新的后端接口。

## 3. 方案

### 3.1 联动方式

采用前端本地联动，不新增后端接口：

1. 用户在会话中心点击某条会话的“Open in audit”
2. 前端把审计中心筛选条件重置为一组面向单会话排障的默认值
3. 使用现有审计接口重新拉取列表

### 3.2 审计筛选默认值

点击联动后，审计中心筛选更新为：

- `payloadQuery = sessionId`
- `eventPrefix = ""`
- `eventType = ""`
- `accountQuery = ""`
- `occurredFrom = ""`
- `occurredTo = ""`
- `limit` 保留当前值

这样做的原因是：

- `payloadQuery = sessionId` 已足以命中聊天与工具运行等会话级事件
- 清空 `eventPrefix` / `eventType`，避免用户先前的局部筛选把联动结果意外过滤掉
- 保留 `limit`，避免干扰当前分页习惯

### 3.3 适用范围

本次联动同时支持：

- 超级管理员工作台
- 租户管理员工作台

两者都继续走各自已有的审计查询接口：

- 超级管理员：`/api/admin/audit/events`
- 租户管理员：`/api/admin/tenant/audit/events`

### 3.4 边界

本次不做：

- 页面自动滚动到审计中心
- 审计中心高亮当前联动来源会话
- 会话中心与审计中心的双向联动
- 新增“仅看该会话 run.*”之类的高级快捷筛选

## 4. 验证

至少覆盖：

1. 会话中心每条记录展示“Open in audit”动作
2. 点击后会触发新的审计请求
3. 请求 URL 带上 `payloadQuery=<sessionId>`
4. 审计中心列表更新为该会话对应的结果
5. 剩余缺口文档同步更新“审计中心 / 会话中心联动”状态
