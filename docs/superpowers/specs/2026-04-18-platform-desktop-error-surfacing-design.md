# Platform Desktop Error Surfacing Design

## 1. 背景

第二阶段桌面端已经切到“租户登录 -> 在线初始化 -> 工作区”的主链路，但当前平台客户端在收到非 2xx 响应时，只会把 `status + statusText` 组装成错误信息。

这会带来两个直接问题：

- 登录失败时，用户只能看到 `401 Unauthorized`，看不到后端返回的明确原因
- 初始化失败时，界面无法展示更贴近业务语义的错误文本，不利于重试与排障

对于当前“必须联网、必须在线初始化、失败要明确阻断”的主流程来说，这个问题会直接影响可用性与运维效率。

## 2. 本次目标

本次只补“错误透传”这一个闭环细节，不扩展新的接口能力。

目标如下：

- 桌面端优先读取平台后端错误响应中的 `message`
- 若后端没有 `message`，则回落到纯文本响应
- 若响应体也不可用，再回落到 `status + statusText`
- 保持现有 `PlatformRequestError.status` 语义不变
- 不改动既有登录、初始化、刷新、审计等业务调用入口

## 3. 范围与非目标

### 3.1 范围

- `src/main/platform/client.ts`
- `tests/platform-runtime.test.ts`

### 3.2 非目标

- 不新增新的平台接口
- 不改动后端错误结构
- 不做错误码国际化映射
- 不改变前端页面状态机

## 4. 设计方案

### 4.1 错误解析顺序

平台客户端在 `fetch` 返回非成功响应时，按以下顺序决定最终错误消息：

1. 若响应体是 JSON，且存在字符串类型的 `message` 字段，则使用它
2. 若响应体是非空纯文本，则使用该文本
3. 否则回落到 `HTTP <status> <statusText>` 风格的默认消息

### 4.2 调用链收益

由于桌面端登录、初始化、刷新和审计上传都统一经过 `src/main/platform/client.ts`，因此只需在这一层补齐错误解析，即可让以下链路同时获益：

- 登录页错误提示
- 初始化页错误提示
- 刷新令牌失败消息
- 审计上传失败消息

## 5. 验证口径

至少覆盖以下用例：

- 登录接口返回 `401` 且响应体为 `{ "message": "invalid credentials" }` 时，运行时抛出 `invalid credentials`
- 初始化阶段某个桌面接口返回非 2xx 且包含 `message` 时，运行时抛出该消息
- 保持 `PlatformRequestError.status` 不丢失
