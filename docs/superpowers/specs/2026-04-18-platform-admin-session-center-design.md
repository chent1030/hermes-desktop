# Platform Admin 会话中心最小视图设计

## 1. 背景

上一顺位切片已经把平台管理端的审计中心打通，并补上了基础筛选与简单分页：

- 平台已经持续接收桌面端运行审计
- 管理端已经能按租户查看审计事件
- 聊天生命周期事件已经进入 `platform_audit_events`

但当前后台仍然只能“按事件看审计”，还不能“按会话看运行过程”。

这会带来两个问题：

1. 运营或管理员很难快速判断某个租户最近有哪些会话在活跃、失败或完成
2. 当前聊天审计虽然已经入库，但会话标识还没有在所有关键事件上形成稳定的一致规则，不利于后续做会话中心、会话诊断和合规追溯

因此下一顺位切片拆成连续两小步，但仍属于同一主题：

1. **先补会话审计主键贯通规则**
2. **再补平台管理端会话中心最小只读视图**

## 2. 方案比较与结论

本次设计阶段评估了三种路径：

### 2.1 方案 A：先补会话审计主键，再做会话中心最小视图（最终选定）

做法：

- 先收敛桌面端聊天审计里的会话标识规则
- 后端继续复用 `platform_audit_events`，按会话维度做最小聚合
- 管理端先做只读会话列表，不引入新大表

优点：

- 顺序最稳，符合当前“一个切片一个切片收口”的推进方式
- 不会过早引入独立会话汇总表，避免查询模型和数据模型同时发散
- 能让后续会话诊断、会话筛选和会话详情都建立在一致的事件主键之上

缺点：

- 首版会话中心能力偏克制，只提供最小可查视图
- 需要先补一层聊天审计契约，再进入管理端 UI

### 2.2 方案 B：直接基于现有审计事件做会话中心

做法：

- 不调整桌面端事件契约
- 后端直接从现有 `payload.sessionId` 聚合会话

不选原因：

- 当前 `chat.started` 并不稳定携带会话标识
- 某些失败链路下会话标识仍可能缺失
- 直接上会话中心会导致视图先天不完整，后面仍然要返工

### 2.3 方案 C：直接引入独立会话汇总表

做法：

- 新建平台会话表
- 审计写入同时维护会话投影
- 管理端只读会话表

不选原因：

- 当前阶段过重
- 会把“事件收集、会话建模、后台视图”三件事一次性耦合起来
- 不符合这一轮“先把链路打稳，再加投影表”的节奏

最终采用：**方案 A**。

## 3. 本次范围

本次只做以下能力：

1. 桌面端聊天生命周期事件补齐最小会话标识规则
2. 平台后端新增会话中心最小查询接口
3. 超级管理员查看指定租户最近会话
4. 租户管理员查看本租户最近会话
5. 管理端新增会话中心最小只读卡片
6. 设计与实现文档补齐

本次明确不做：

- 会话全文回放
- 聊天 transcript 展示
- 会话级导出
- 会话详情页
- 会话统计图表
- 独立会话汇总表
- 工具调用时间线
- 按账号 / 时间范围 / 状态做复杂筛选

也就是说，本次只做“先能按会话看”，不做“会话中心完整版”。

## 4. 会话审计主键规则

### 4.1 当前问题

当前桌面端聊天审计大致如下：

- `chat.started`
- `chat.completed`
- `chat.failed`

但问题是：

- `chat.started` 当前只带消息长度、模型 profile、`resumeSessionId`
- `chat.completed` 才会在成功时拿到真正的 `sessionId`
- `chat.failed` 在失败较早时可能没有真正的 `sessionId`

这意味着平台虽然能看到聊天事件，但还缺少稳定、明确的“会话归属规则”。

### 4.2 本次采用的最小规则

本次不发明新的跨端全局会话 ID，也不引入新的本地持久化映射表。

本次统一约定如下：

1. `chat.completed` 必须继续上报真实 `sessionId`
2. `chat.started` 若属于继续已有会话，则显式带上 `sessionId = resumeSessionId`
3. `chat.failed` 若属于继续已有会话，则显式带上 `sessionId = resumeSessionId`
4. `chat.started / chat.failed / chat.completed` 继续保留 `resumeSessionId` 字段，便于问题排查
5. 若是全新会话且在获得真实 `sessionId` 前就失败，则本次允许该条事件没有最终会话主键，不强行补一套临时 ID 机制

这样做的含义是：

- **已存在会话** 的后续聊天链路，平台可以稳定归属到同一个 `sessionId`
- **新建成功的会话**，平台至少能从 `chat.completed` 开始识别出真实会话
- **新建且在建链前失败的会话**，本次暂不纳入会话中心，只保留在审计中心中查看

这是一个有意收敛范围的设计，目的是先保证已形成会话主键的主链路稳定可查。

## 5. 平台会话中心数据模型

本次继续复用 `platform_audit_events` 作为唯一数据来源，不新增会话表。

### 5.1 会话识别范围

会话中心只聚合具备可识别会话主键的聊天事件：

- `event_type` 以 `chat.` 开头
- `payload.sessionId` 非空

首版不从其他字段做复杂推断，也不对无主键事件做修补归并。

### 5.2 最小会话汇总结构

后端返回给管理端的最小会话结构建议如下：

- `sessionId`
- `tenant`
- `lastAccount`
- `lastEventType`
- `lastOccurredAt`
- `eventCount`
- `hasFailure`

字段含义：

- `sessionId`：本次会话中心的唯一主键
- `tenant`：租户最小信息，返回 `id / code / name`
- `lastAccount`：最后一个触发该会话事件的账号，返回 `id / username / displayName / roleCode`
- `lastEventType`：该会话最近一条事件类型
- `lastOccurredAt`：该会话最近一次事件时间
- `eventCount`：当前已入库并能归属到该 `sessionId` 的事件总数
- `hasFailure`：是否出现过 `chat.failed`

### 5.3 聚合规则

后端按以下规则做最小聚合：

- 过滤当前 actor 有权访问的租户范围
- 只统计 `payload.sessionId` 非空的 `chat.*` 事件
- 以 `payload.sessionId` 分组
- 每组取最近事件作为 `lastEventType / lastOccurredAt / lastAccount`
- 组内若出现过 `chat.failed`，则 `hasFailure = true`
- 按 `lastOccurredAt DESC, sessionId DESC` 返回最近会话

## 6. 查询接口设计

### 6.1 超级管理员接口

- `GET /api/admin/sessions?tenantId=<id>&limit=<n>`

规则：

- 必须带 `tenantId`
- 默认只看指定租户
- 不支持全平台无条件扫表

### 6.2 租户管理员接口

- `GET /api/admin/tenant/sessions?limit=<n>`

规则：

- 服务端自动绑定当前租户
- 不允许跨租户查询

### 6.3 limit 规则

- 默认 `100`
- 最大 `200`
- 小于等于 `0` 回落默认值

本次先不做会话分页游标；如果需要继续向后翻，会在后续切片补上。

## 7. 管理端前端设计

### 7.1 超级管理员工作台

新增卡片：

- 标题：`Session center`
- 行为：
  - 未选租户时，显示提示“Select a tenant to inspect runtime sessions.”
  - 已选租户时，加载最近会话列表

每个列表项最小展示：

- `sessionId`
- 最近事件类型
- 最近账号
- 最近时间
- 事件数
- 若 `hasFailure = true`，显示失败标记

### 7.2 租户管理员工作台

新增卡片：

- 标题：`Tenant session center`
- 自动加载本租户最近会话
- 不显示跨租户切换能力

### 7.3 与审计中心的边界

本次会话中心和已有审计中心并列存在：

- 审计中心继续回答“发生了哪些事件”
- 会话中心回答“最近有哪些会话、状态如何”

本次不做两者之间的点击联动，不做“点会话跳审计详情”。

## 8. 测试策略

至少覆盖以下内容：

1. 桌面端聊天审计在恢复已有会话时，`chat.started` 显式携带 `sessionId`
2. 桌面端聊天失败时，若存在 `resumeSessionId`，`chat.failed` 也显式携带 `sessionId`
3. 后端能按 `payload.sessionId` 聚合最近会话
4. 超级管理员缺少 `tenantId` 时不能查询会话中心
5. 租户管理员只能查看本租户会话
6. 前端显示 `Session center / Tenant session center` 卡片
7. 定向测试、全量测试、真实 PostgreSQL ignored 测试继续通过

## 9. 后续演进边界

完成这一小步后，平台后台将从“只能按事件看审计”升级为“既能按事件看，也能按会话看”。

后续再继续扩展：

- 会话详情抽屉 / 详情页
- 与审计中心联动
- 会话筛选与分页
- transcript 摘要与诊断信息
- 工具调用时间线
- 独立会话汇总表或物化投影

这样可以先把“会话主键规则”和“会话最小视图”稳稳落下，再逐步扩大会话中心能力。
